### Added — safe `aipm update` transaction workstream

Repository-level implementation of the production roadmap's safe `aipm update` transaction, in published `main` order. All of this work is repository evidence only: implemented and tested in the repository, not deployed, with no live-VPS validation and no production execution.

- **Restore points and deterministic rollback** (2026-09-03, `fabb6e6` — "feat: add safe update restore and rollback"): `RollbackManager` (`src/aipm/services/update/rollback.py`) restores project files from a `BackupEngine` snapshot archive; it restores exactly the regular files captured in the snapshot, never deletes anything, keeps `.git`, volumes, databases, and runtime state out of scope, and fails closed on non-regular, symlink, path-traversal, or foreign-prefix archive members. The update engine's failure path automatically restores from the pre-update snapshot and records the outcome in `UpdateAudit.restore`. Regression coverage: `tests/test_update_rollback.py` (10 tests).
- **Independent update verifier** (2026-09-03, `f02440b` — "feat: add independent update verifier"): `UpdateVerifier` (`src/aipm/services/update/verifier.py`) is a distinct component from planning and execution; it compares health-before and health-after reports and returns a typed success/warning/failure verdict. Warnings are explicitly not rollback conditions; critical findings or an unevaluatable post-update state fail safe into the same rollback path as an execution failure, and the verdict is recorded additively in `UpdateAudit.verification`. Regression coverage: `tests/test_update_verifier.py` (11 tests).
- **Git transaction hardening** (2026-09-03, `e508143` — "feat: harden update git transactions"): `GitTransactionRunner` (`src/aipm/services/update/git_transaction.py`) runs the update's Git phases (safety stash including untracked files, fetch, pull, stash apply, stash drop) as one classified transaction. The stash is dropped only after a successful apply; on apply failure the stash is preserved for manual recovery and the exact conflicting files are enumerated read-only. No checkout/reset/clean runs anywhere in the transaction, and every failure raises a typed `GitTransactionError` recorded in `UpdateAudit.git_transaction`. Regression coverage: `tests/test_update_git_transaction.py` (13 tests).
- **Service and capability separation** (2026-09-03, `1f32b61` — "refactor: separate update capability from engine"): `UpdateEngine` is presentation-free (no Rich imports or console printing); all operator-facing output for `aipm update` moved to the `UpdateCapability` layer (`src/aipm/capabilities/update/commands.py`), and the engine returns typed outcomes instead of printing. A fail-closed plan-reuse contract makes the engine refuse a plan whose project or dry-run flag does not match the requested execution, so the operator approves exactly the plan that runs. Regression coverage: `tests/test_update_separation.py` (11 tests).
- **Upstream Git change analysis** (2026-09-03, `5866ce4` — "feat: analyze upstream git changes before update"): `GitProvider.remote_changed_files` (`src/aipm/providers/git/provider.py`) classifies what an incoming pull would change via a strictly read-only three-dot diff against the already-fetched tracking ref, returning `None` when the analysis cannot be performed read-only so callers fail closed. Incoming critical-infrastructure changes block the update and name the exact files; unanalyzable incoming state forces manual review. Regression coverage: `tests/test_update_remote_analysis.py` (7 tests).
- **Runtime-action preflight** (2026-09-03, `a123a99` — "feat: add runtime preflight to update planner"): `UpdatePlanner._analyze_compose_runtime` statically preflights the Compose rebuild action from disk (`yaml.safe_load`; no Docker daemon, no external processes, no network) and names the exact services a rebuild would affect. Missing, unparseable, non-mapping, or service-less Compose declarations block the update fail-closed through the existing plan-risk chain. Regression coverage: `tests/test_update_runtime_preflight.py` (8 tests).
- **Disposable update integration fixtures** (2026-09-04, `25628d7` — "test: add disposable update integration fixtures"): `tests/update_fixtures.py` provides disposable builders (work repository with a bare remote under `tmp_path`, remote-commit builder, hermetic health-engine wiring, Compose project-layout builder, a `GuardCompose` tripwire, and real-pipeline wiring with all snapshots and audit records confined to the fixture tree), and `tests/test_update_integration.py` runs the previously unit-faked pipeline end-to-end (8 tests) with real Git remotes and no Docker daemon contact.
- **CI and release hygiene** (2026-09-04, `41c2864` — "ci: add validation workflow and release hygiene"): added a validation-only GitHub Actions workflow (`.github/workflows/ci.yml`; push to `main` and `pull_request` triggers only, `permissions: contents: read`, 30-minute job timeout, actions pinned by full commit SHA, `persist-credentials: false`, the full pytest suite with no exclusions, and the existing release chain `ops/validate-release.py --development` → `ops/build-release.py` → `ops/validate-release.py` reused verbatim). The workflow posture is certified by `tests/test_ci_workflow.py` (16 tests). Also added `CONTRIBUTING.md` (setup, no-exclusions test contract, known host-state-dependent tests, release-validation chain, commit conventions, no-secrets rule) and `SECURITY.md` (CI trust boundary, vulnerability reporting, security-relevant contracts, execution-plane denial). The workflow publishes nothing; GitHub-hosted execution of the workflow has not been observed from this repository's environment and is a fact about the remote CI, not repository state.

### Fixed — Mission Control reliability

- **MC-6.12 privilege boundary and service-runtime scope hardening** (2026-09-01, `ee308ac` — "MC-6.12 harden privilege boundary and service runtime scopes"): hardened the MC-6.12 privilege boundary and service-runtime scopes in published history.
- **Mission Control telemetry reliability remediation** (2026-09-02, `43e4403` — "fix: remediate mission control telemetry reliability"): fixed the chain of defects that left the read-only cockpit without project telemetry and with frozen project freshness — the telemetry unit lacked `AIPM_CONFIG` and discovered no projects; Git enrichment ran against repositories without a per-invocation `safe.directory` exception and one failure failed entire project discovery; the dashboard never re-read persisted project telemetry so freshness stayed frozen until restart; network telemetry required `AF_NETLINK` under sandboxing; and log-source configuration needed to honor `AIPM_LOG_FILE`. The remediation is bounded and additive (no schema migration), was deployed on the VPS and runtime-validated per `docs/MC-6.12_TELEMETRY_REMEDIATION.md`, and carries a documented host-permission residual (unreadable `aipm` Git ref metadata) that degrades gracefully and is never auto-repaired.

## Historical milestones

### Read-only Mission Control cockpit (MC-1.5 through MC-6.13 Phase 4E)

The read-only Mission Control cockpit is substantially landed: dashboard, host/server intelligence, Docker, projects, allow-listed Systemd observation, bounded redacted logs, incidents, history, settings posture, notifications surfaces (delivery disabled), the read-only TUI, and the deterministic non-authoritative advisor. Observation routes are GET-only; dashboard SQLite access is read-only/query-only; telemetry sampling is telemetry-owned; and the advisor performs no LLM/provider execution and takes no actions. The milestone-by-milestone ledger with publication evidence is maintained in [`docs/CURRENT_STATUS.md`](docs/CURRENT_STATUS.md). Representative published commits: MC-6.11 read-only notifications TUI view (`bbd8fef`, 2026-08-26), MC-6.13 Phase 4E production validation record (`3c34e42`, 2026-08-26), read-only SQLite WAL-sidecar fix (`1c1cc4d`, 2026-08-28), and pagination/systemd-scope/notification-schema provisioning fixes (`8f22aa0`, 2026-08-28).

### 2026-08-31 — MC-6.12 staging-only control plane and execution-plane release

Published lineage: MC-6.12 Stage 2 control-plane foundation (`5e4442b`, 2026-08-27), Stage 3 owner control plane (`052d473`, 2026-08-28), and the execution-plane release (`a8559b4`, 2026-08-31 — "release: MC-6.12 execution plane"): a durable SQLite control-plane store (plans, decisions, actions, leases, snapshots, verification evidence, kill-switch state), bounded `{title, objective}` project-plan mutations with compare-and-set revisions and digests, independent read-back verification, CAS-guarded rollback against immutable pre-mutation snapshots, a hashed audit chain, a localhost-only authenticated operator transport (Argon2id owner login, server-side sessions, CSRF on state changes, bounded 429 rate limiting on authorize/confirm), and a durable kill switch seeded engaged for staging and permanently engaged for production.

The executor path remains unimplemented and denied: production actions are refused, no production IPC executor is deployed, plans are hard-restricted to staging, no action API/UI is exposed on the public vpanel, and production authorization remains denied. Follow-up hardening in the same window covered release tooling correctness (`ffea142`), the artifact-built-before-deployment release contract (`a6b3891`), cutover tooling hardening (`51ac78b`), and AIPM identity provisioning (`4158ed3`); operator-transport rate limiting is additionally enforced by dedicated regression tests (`c04c017`, 2026-09-03).

## Safety boundaries and deferred work

Safety boundaries in force across everything above: Mission Control observes the VPS and does not change it; the MC-6.12 executor and production action plane remain unimplemented and denied; `DATABASE_MERGE`, `DATABASE_DELETE`, and `PRODUCTION_DATA_REPAIR` are `NOT_AUTHORIZED`; `AUTONOMOUS_REMEDIATION`, `LLM_ASSISTED_EXECUTION`, and `PROVIDER_DRIVEN_EXECUTION` are `FORBIDDEN`; notification delivery remains disabled.

Deliberately deferred (documented in the 2026-09-04 reconciliations): an upgrade guide, release-checklist consolidation (`docs/MC-6.12_RELEASE_AND_CUTOVER.md` already exists), dependency and secret scanning (pip-audit/gitleaks), and any publishing automation. Separately approved real-VPS read-only integration remains blocked on credentials and explicit approval; MC-6.12 operational execution and MC-6.13 post-4E remain denied by their own roadmap gates.
