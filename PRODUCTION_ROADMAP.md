# AIPM Production Roadmap

**Assessment date:** 2026-08-16
**Repository state:** local `main` at `df4e909` (`Complete AIPM core workflows and documentation`)
**Source of requirements:** attached `AIPM.md`, especially sections 2, 5, 7–11, 15, and 18.

## Current-state assessment

AIPM has a usable Python/Typer foundation with configuration, logging, project discovery, Docker and Compose providers, Git state models, health analyzers, backups, and an update command. The previous completion pass made the package installable, removed the undeclared Compose dependency, added deterministic unit coverage, and improved error handling. The repository is clean locally and contains no tracked virtual environment or generated bytecode.

The attached production brief changes the completion target in an important way: **`aipm update` is the primary product**, and it must become a safe management transaction for an existing VPS rather than a generic Compose restart command. The current update implementation is still too small for that responsibility. It performs a pre-update snapshot, blocks dirty Git repositories, rebuilds one custom runtime or one Compose project, and runs a compatibility health check. It does not yet build a complete update plan, support dry-run or explicit approval, analyze upstream changes, produce an audit record, or provide a deterministic rollback transaction.

The real infrastructure paths named in the brief (`/home/ubuntu/local-ai-packaged`, `/home/ubuntu/cloudflared`, `/home/ubuntu/openvpn`, `/home/ubuntu/color-mixer`, and `/home/ubuntu/product-tracker`) are absent from the sandbox. The legacy `update.sh`, `start_services.py`, and infrastructure Compose files were therefore not available for inspection. No connection to the real VPS was attempted, and no production state was changed. The implementation below is consequently designed from the stated contracts and local repository behavior; it must receive a read-only VPS inspection and the real operational scripts before production execution is enabled.

## First implementation milestone

The first production milestone is **safe update planning and dry-run execution**. It should not touch the production VPS. It should add a typed `UpdatePlan` that records project identity, health-before summary, Git state, Compose/runtime actions, snapshot requirement, risk, reasons, and approval requirement. A planner should construct that model without side effects. A renderer/capability should display it. The update command should support:

```text
aipm update <project> --dry-run
aipm update <project> --yes
```

The default command should display the plan and stop unless `--yes` is provided. `--dry-run` should explicitly prohibit all state-changing operations. The executor should remain behind services/providers and should only run after the plan has passed deterministic safety checks and explicit approval. This milestone should also persist a redacted JSON audit record for dry-run and execution outcomes.

## Ordered roadmap

### P0 — Safe planning and approval

Implement `UpdatePlanner`, `UpdatePlan`, dry-run output, explicit approval, risk classification, and audit records. Replace ad-hoc update decisions with typed plan data. Ensure no provider mutation is reachable from dry-run.

### P0 — Git transaction safety

Extend Git analysis to classify critical infrastructure changes, remote divergence, conflicts, detached heads, existing stashes, and safe local changes. Implement a transaction that preserves the stash when application conflicts occur and reports the exact conflicting files.

### P1 — Update execution and verification

Split execution into snapshot, fetch/pull, image pull/build, runtime restart, and verification steps. Add a verifier that compares health-before and health-after reports and returns success, warning, or failure without treating every warning as a rollback condition.

### P1 — Explicit rollback and restore points

Define what a snapshot contains, how it is restored, and which resources are intentionally outside its scope. Implement a rollback manager that can restore AIPM-managed configuration and return the infrastructure to the last known operational state without silently deleting volumes or databases.

### P1 — Real VPS read-only integration

After credentials are rotated and the user explicitly requests access, inspect the production environment read-only: repository status, Compose configuration, services, images, volumes, networks, disk, memory, systemd status, `update.sh`, and `start_services.py`. Store only redacted operational metadata in audit artifacts. Do not run `compose up/down`, `git pull`, package upgrades, pruning, or deletion during inspection.

### P2 — Integration testing and release readiness

Add disposable Git remote fixtures and Docker Compose fixtures, then add CI for tests, packaging, static checks, and security scans. Complete contribution, upgrade, changelog, release, and security documentation. Verify that no keys, tokens, host-specific secrets, or generated environments are committed.

## Decision boundary

The project should not be declared production-ready merely because the CLI works locally. The first milestone is complete only when a dry-run is demonstrably side-effect-free, a normal update requires explicit approval, critical Git changes block safely, and every planned/executed update has a structured audit record. Real-VPS execution remains a separate, approval-gated milestone after read-only inspection of the actual infrastructure.
