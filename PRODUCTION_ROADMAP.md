## Current-state reconciliation — 2026-09-03 (upstream change analysis landed)

Local-change classification already existed; the new piece classifies what an incoming pull would change, without contacting the remote. `GitProvider.remote_changed_files` (`src/aipm/providers/git/provider.py`) performs a strictly read-only three-dot diff (`HEAD...origin/<branch>`) against the already-fetched tracking ref: no fetch, no pull, no worktree mutation, and it returns `None` when the analysis cannot be performed read-only (detached HEAD, missing origin, missing tracking ref, or Git error) so callers fail closed instead of assuming nothing is incoming. `GitService.prepare_update` (`src/aipm/services/git/service.py`) consumes it: unanalyzable incoming state (with a configured remote) forces manual review (`proceed=False`); incoming changes touching critical infrastructure files block the update and name the exact files; non-critical incoming changes are enumerated in the plan reasons ("N file(s) will change on pull: …") without blocking. Because the existing `GitUpdatePlan.review_required` flag already drives the planner's typed `BLOCKED` risk and the engine's no-execution refusal path, no planner, engine, model, or capability changes were required — the analysis plugs into the existing fail-closed chain. ## Current-state reconciliation — 2026-09-03 (independent update verifier landed)

The P1 **"Update execution and verification"** verifier item is now implemented at repository level, per the roadmap requirement to "add a verifier that compares health-before and health-after reports and returns success, warning, or failure without treating every warning as a rollback condition." The new `UpdateVerifier` (`src/aipm/services/update/verifier.py`) is a distinct component from planning and execution: it is injected into the update engine, and the engine consumes its typed verdict (`UpdateVerification`, `src/aipm/models/verification.py`) instead of deciding success itself. Verdict semantics: SUCCESS = no warning-or-worse post-update findings; WARNING = high/warning findings without critical ones (explicitly not a rollback condition; the update remains successful); FAILURE = critical post-update findings — the same condition that already drove the engine's rollback path — or an unevaluatable post-update state (missing health-after report, verifier error), which fails safe. A verification FAILURE enters the same rollback path as an execution failure: the pre-update snapshot is restored and the audit record preserves the execution result, the verification result (`UpdateAudit.verification`, additive), and the restore result (`UpdateAudit.restore`) as distinct fields. Verification is read-only with respect to the project: it analyzes already-produced health reports and never runs commands or mutates state. Regression coverage: `tests/test_update_verifier.py` (11 tests) covers verdict semantics, fail-safe verifier errors, read-only behavior, planner/executor independence, engine consumption, rollback on verification failure, and audit preservation. This remains repository-only work: not deployed, no live-VPS validation, the MC-6.12 executor and production action execution remain unauthorized and unimplemented.

## Current-state reconciliation — 2026-09-03 (P0 Git transaction safety landed)

The P0 **"Git transaction safety"** workstream is now implemented at repository level, per the roadmap requirement to "implement a transaction that preserves the stash when application conflicts occur and reports the exact conflicting files." The previously dead `GitTransactionResult` model (`src/aipm/models/git_transaction.py`) is completed (adds `stash_preserved`) and is now the typed outcome of the update's Git phases: stashed, pulled, stash_applied, stash_preserved, conflicts, warnings, and errors. The new `GitTransactionRunner` (`src/aipm/services/update/git_transaction.py`) runs those phases — safety stash (with untracked files, `-u`), fetch, pull, stash apply, stash drop — as one classified transaction around the update engine's runtime execution. Contract: the stash is dropped only after a successful apply; on any apply failure the stash is preserved for manual recovery and the exact conflicting files are enumerated read-only (`GitService.conflicted_files`, no mutation to "make the update work"); on fetch/pull failure with a stash present the local changes remain preserved in the stash. Every failure raises `GitTransactionError` (`src/aipm/core/exceptions.py`, an `UpdateError` subclass) carrying the typed result, so failure classification never depends on exception text alone. The update engine records the transaction additively in the audit record (`UpdateAudit.git_transaction`), alongside the existing error/restore/verification fields; a Git-transaction failure enters the same snapshot-restore rollback path as any execution failure, and the operator's changes are never silently discarded — no checkout/reset/clean runs anywhere in the transaction, and untracked files are stashed and reapplied rather than deleted. The provider already refused pulls on dirty trees, classifies critical-file modifications at plan time (manual review, no stash), and enumerates conflicts via the Git index, so this slice completes the typed transaction and exact-conflict reporting rather than duplicating those mechanisms. Regression coverage: `tests/test_update_git_transaction.py` (13 tests) uses disposable temporary Git repositories to cover clean-repo updates, dirty-tracked + untracked operator changes stashed/applied/dropped with content preserved, pulls, conflicting pull targets (exact file reported, stash preserved, operator content recoverable from the stash), fetch/pull failure (stash preserved), stash failure, conflict-enumeration failure not masking the apply error, engine git-failure rollback with typed audit capture, success/verification-failure/runtime-failure/no-git audits, and a source-level check that the transaction introduces no destructive Git commands (no clean/reset --hard/checkout -- /restore .). This remains repository-only work: not deployed, no live-VPS validation, and no network/service operations beyond local disposable fixtures.

## Current-state assessment

AIPM has a usable Python/Typer foundation with configuration, logging, project discovery, Docker and Compose providers, Git state models, health analyzers, backups, and an update command. The previous completion pass made the package installable, removed the undeclared Compose dependency, added deterministic unit coverage, and improved error handling. The repository is clean locally and contains no tracked virtual environment or generated bytecode.

The attached production brief changes the completion target in an important way: **`aipm update` is the primary product**, and it must become a safe management transaction for an existing VPS rather than a generic Compose restart command. The current update implementation is still too small for that responsibility. It performs a pre-update snapshot, blocks dirty Git repositories, rebuilds one custom runtime or one Compose project, and runs a compatibility health check. It does not yet build a complete update plan, support dry-run or explicit approval, analyze upstream changes, produce an audit record, or provide a deterministic rollback transaction.

The real infrastructure paths named in the brief (`/home/ubuntu/local-ai-packaged`, `/home/ubuntu/cloudflared`, `/home/ubuntu/openvpn`, `/home/ubuntu/color-mixer`, and `/home/ubuntu/product-tracker`) are absent from the sandbox. The legacy `update.sh`, `start_services.py`, and infrastructure Compose files were therefore not available for inspection. No connection to the real VPS was attempted, and no production state was changed. The implementation below is consequently designed from the stated contracts and local repository behavior; it must receive a read-only VPS inspection and the real operational scripts before production execution is enabled.

## First implementation milestone

The first production milestone is **safe update planning and dry-run execution**. It should not touch the production VPS. It should add a typed `UpdatePlan` that records project identity, health-before summary, Git state, Compose/runtime actions, snapshot requirement, risk, reasons, and approval requirement. A planner should construct that model without side effects. A renderer/capability should display it. The update command should support:

```text
aipm update <project> --dry-run
aipm update <project> --yes
```

The default command should display the plan and stop unless `--yes` is provided. `--dry-run` should explicitly prohibit all state-changing operations. The executor should remain behind services/providers and should only run after the plan has passed deterministic safety checks and explicit approval. This milestone should also persist a redacted JSON audit record for dry-run and execution outcomes.

## Ordered roadmap

### P0 — Safe planning and approval

Implement `UpdatePlanner`, `UpdatePlan`, dry-run output, explicit approval, risk classification, and audit records. Replace ad-hoc update decisions with typed plan data. Ensure no provider mutation is reachable from dry-run.

### P0 — Git transaction safety

Extend Git analysis to classify critical infrastructure changes, remote divergence, conflicts, detached heads, existing stashes, and safe local changes. Implement a transaction that preserves the stash when application conflicts occur and reports the exact conflicting files.

### P1 — Update execution and verification

Split execution into snapshot, fetch/pull, image pull/build, runtime restart, and verification steps. Add a verifier that compares health-before and health-after reports and returns success, warning, or failure without treating every warning as a rollback condition.

### P1 — Explicit rollback and restore points

Define what a snapshot contains, how it is restored, and which resources are intentionally outside its scope. Implement a rollback manager that can restore AIPM-managed configuration and return the infrastructure to the last known operational state without silently deleting volumes or databases.

### P1 — Real VPS read-only integration

After credentials are rotated and the user explicitly requests access, inspect the production environment read-only: repository status, Compose configuration, services, images, volumes, networks, disk, memory, systemd status, `update.sh`, and `start_services.py`. Store only redacted operational metadata in audit artifacts. Do not run `compose up/down`, `git pull`, package upgrades, pruning, or deletion during inspection.

### P2 — Integration testing and release readiness

Add disposable Git remote fixtures and Docker Compose fixtures, then add CI for tests, packaging, static checks, and security scans. Complete contribution, upgrade, changelog, release, and security documentation. Verify that no keys, tokens, host-specific secrets, or generated environments are committed.

## Decision boundary

The project should not be declared production-ready merely because the CLI works locally. The first milestone is complete only when a dry-run is demonstrably side-effect-free, a normal update requires explicit approval, critical Git changes block safely, and every planned/executed update has a structured audit record. Real-VPS execution remains a separate, approval-gated milestone after read-only inspection of the actual infrastructure.
